# 보충: BeginReady와 MRT209 재사용의 성능 상충

2026-11-13 · 기존 a33 대응 소스의 6개 관련 파일 identity를 재확인했다. 기존 감사보고서는 보존했고 소스·빌드·게임·테스트 실행은 하지 않았다.

1. **정적 연결은 확정이다.** [WorldRenderer:2397](https://github.com/yeojuny/BAR-Metal4/blob/a33ebfe888bc8abe0053df05e5e2892c0788d6a8/engine/rts/Rendering/Metal4/Metal4WorldRenderer.mm#L2397)은 `options.allowBeginReady`가 true이면 frontier를 만들지 않으며, 최종 `Eligible()`는 2410–2418에서 계산한다. 따라서 요청은 됐으나 실제 pilot은 부적격인 경우도 209 permission을 잃을 수 있다.
2. 다만 환경변수 ON이 모든 경로에서 곧 `allowBeginReady=true`인 것은 아니다. [SceneBridge:2131](https://github.com/yeojuny/BAR-Metal4/blob/a33ebfe888bc8abe0053df05e5e2892c0788d6a8/engine/rts/Rendering/Metal4/Metal4SceneBridge.cpp#L2131)의 admission·dynamic/legacy water 제한을 먼저 지난 경로에 대한 결론이다.
3. [OpaqueModelSource:305](https://github.com/yeojuny/BAR-Metal4/blob/a33ebfe888bc8abe0053df05e5e2892c0788d6a8/engine/rts/Rendering/Metal4/Metal4OpaqueModelSource.mm#L305) → [MRTWriteReuse209:33](https://github.com/yeojuny/BAR-Metal4/blob/a33ebfe888bc8abe0053df05e5e2892c0788d6a8/engine/rts/Rendering/Metal4/Metal4MRTWriteReuse209.h#L33)의 null-frontier 거절 → [CUSDeferred:254](https://github.com/yeojuny/BAR-Metal4/blob/a33ebfe888bc8abe0053df05e5e2892c0788d6a8/engine/rts/Rendering/Metal4/Metal4CUSDeferred.mm#L254)의 readonly/쓰기재사용/COW 선택 → 339–353의 prior-content copy로 연결된다.
4. **추가 비용의 조건은 OFF 경로라면 원래 209를 통과할 정확한 U→F model writing phase라는 것이다.** source/frame/submission/view/physical-owner·fresh-publication·no-reader 검사가 모두 필요하다. engine writer가 있거나, Lua-only writer이면 `BAR_NATIVE_INTERVENTION_MRT_LUA_REUSE=1`과 실제 prepared Lua draw 조건이 필요하다(MRTWriteReuse209:46–72, CUSDeferred:70–99).
5. readonly164를 통과한 빈 feature phase는 요청 ON이어도 prior storage를 계속 빌린다. 원래 209 부적격 phase도 이 guard 때문에 새로 비용이 늘었다고 할 수 없다. clearBefore/증명된 discard로 prior 보존이 불필요한 attachment에는 copy가 없다(CUSDeferred:45–67,194–228,335–353).
6. 원래 209를 통과할 load-preserving writing F에서는 별도 pool storage 선택과 5 color+depth 보존 copy가 다시 생길 수 있다. 이는 **조건부 큰 비용 후보**이며, 모든 frame에서 6copy·새 물리 allocation이 발생한다거나 현재 실측 병목이라는 뜻은 아니다. 발생 빈도·해상도·pool hit·GPU 시간·평균 FPS 기여는 미측정이다.
7. 따라서 현 BeginReady ON/OFF 비교는 CPU Encode overlap 이득과 MRT copy/storage 비용을 함께 바꿀 수 있다. 평균 FPS 차이를 CPU overlap만의 효과로 귀속하면 안 된다. actual eligibility, readonly/write-reuse/COW 분기, copy calls/논리 bytes, pool new/reuse를 기존 관측 범위에서 함께 구분해야 한다.
8. **guard 삭제나 옛 frontier의 async 전달은 안전한 해결이 아니다.** 기존 proof는 sealed normal-main과 이후 source writer 부재에 의존한다(MRTWriteReuse209:18–22,122–134). GPU pending1이나 shared_ptr 생존만으로 N+1 capture의 새 reader·publication·rollback과 과거 content overwrite가 안전해지지 않는다.
9. P5 확대 전에 capture/journal과 MRT consumer가 공유할 좁은 계약을 고정한다: exact source/storage version·view, 현재 및 이후 old-content reader의 허용 범위, 쓰기 허가의 예약/소비 시점, 취소·실패 시 owner 보존. 증명되지 않은 reader 또는 publication 전이는 COW로 남긴다. 전체 P6 완료를 선행 조건으로 요구하는 것은 아니다.
10. **기존 AUDIT 8절 순서의 4번(U3/U4) 안에서 이 MRT permission 경계를 먼저 정의하고, 5번(P5 비교·확대)의 선행 조건으로 둔다.** 1번 재현 고정·2번 현 R1/수명 검증은 유지한다. Postprocess/CUS static-sharing 작업도 같은 reader 계약을 보존한다. 부적격 요청의 sync fallback에서 209 복원은 실제 동기성·callback/정산 경계를 증명한 별도 변경으로만 검토한다.
11. 최소 후속 검증은 qualified writing F / readonly F / Lua-only flag ON·OFF / extra old-content reader / requested-but-ineligible를 구분하고, paused N + N+1 capture·abort 및 failed notice에서 permission/old pixels/owner 보존을 확인하는 것이다. 그 뒤 동일 출력·설정의 평균 FPS와 추가 copy 비용을 함께 평가한다. 이번에는 실행하지 않았다.
12. 현재 a33의 새 확정 P0/P1 GPU 결함 없음, Minimal의 R1 조건부 충돌은 현재 수정됨, mac9는 remote 포함이라는 기존 결론은 그대로다.
