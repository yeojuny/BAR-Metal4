# MVK3 / Native Metal4 — 순차적 차등 실행 감사 계획

작성일: 2026-11-15, America/Los_Angeles.

**목표: 현재 같은 Ultra 교전에서 Native가 MVK3보다 늦게 프레임을 진행하는 큰 원인 하나를 확인하고, 그 원인부터 수정한다.**

이 문서는 실행 계획이다. 새 코드 감사의 완료 보고, 성능 패치, 실측 결과가 아니다. 문서 게시 과정에서 새 엔진 빌드·게임·프로파일·벤치마크를 실행하지 않는다. 기존 감사 자료는 아래 고정 커밋 링크로 참조하며, 원자료 전체를 다시 독립 검증했다고 주장하지 않는다.

## 1. 운영 방식을 바꾼다: 한 번에 하나의 성능 가설

기존 실험 PR에 다음 후보를 계속 누적하지 않는다. 순서는 다음으로 고정한다.

```text
0. 기존 비교 기준 확인
   ↓
1. 같은 장면의 실제 작업과 CPU–GPU 시간 관계 비교
   ↓
2. 가장 큰 차이 하나 선정 + 필요한 원인 분리 실험
   ↓
3. 관련 양쪽 코드 비교 + 그 원인 하나의 수정
   ↓
4. 동일 조건 검증 → 채택 / 보류 / 기각
   ↓
채택한 기준 또는 유지한 기존 기준에서 다음 원인을 선택
```

**순차적이라는 것은 한 PR을 끝없이 키우거나, 검증되지 않은 성능 후보를 다음 후보의 필수 기반으로 삼지 않는다는 뜻이다.** 하나의 수정이 성립하려면 함께 바뀌어야 하는 상위 계약·하위 호출부·테스트는 같은 변경에 포함한다. 파일마다 PR을 쪼개거나 불완전한 소유권 계약을 먼저 병합하라는 뜻이 아니다.

- 동시에 활성화하는 성능 가설은 하나다. 자료 읽기·오프라인 분석은 나눠 할 수 있지만, 서로 다른 성능 변경과 게임 측정을 섞지 않는다.
- 다음 단계는 앞 단계의 결과를 읽고 정한다. CPU 최적화 → GPU 최적화처럼 구현 순서를 미리 확정하지 않는다.
- 각 단계의 결과는 고정 커밋으로 보존한다. 다음 단계 문서가 앞 단계 결과를 참조한다.
- 현재 PR #5의 계측, #6의 조회 후보, #7의 저장 공간 후보와 기존 증거는 보존한다. 이 계획은 그 PR들을 병합·종료·기본 활성화하지 않는다.
- 문서·증거 PR과 성능 코드 PR을 구분한다. 측정용 소스 변경이 꼭 필요하면 최소 계측 변경임을 별도로 밝힌다.
- 실패한 후보의 코드를 다음 기준에 자동 편입하지 않는다. 다만 이미 측정한 기준 바이너리에 들어 있는 코드·플래그를 임의로 바꾸지도 않는다. 기준을 바꾸면 새 source/binary/settings identity로 별도 기록한다.

## 2. 현재 확인된 사실과 아직 모르는 것

아래는 외부 감사 인계서가 보고한 값이다. 이 계획의 새 측정값이 아니다. [S1], [S2]

| 비교 | MVK3 평균 FPS | Native 평균 FPS | 해석 |
|---|---:|---:|---|
| 현재 Seths 교전 · Ultra · AA0 | 약 93.87 | 약 47.62 | 같은 현재 조건의 직접 비교 |
| 현재 Seths 교전 · Ultra · 4× AA | 약 68.63 | 약 36.66 | 같은 현재 조건의 직접 비교 |
| 건설 참고 | 과거 약 226.02 | 현재 약 184.96 | 동시 재측정이 아니므로 참고만 사용 |

AA0의 평균 FPS 역수는 약 10.65ms와 21.00ms다. 약 10.35ms 차이는 **CPU 관찰 처리 주기의 차이**이지, GPU 독점 실행 시간이나 그대로 제거 가능한 시간 예산이 아니다.

PR7의 별도 풀 실험은 건설 약 −0.065%, 전투 약 +0.138%로 FPS 향상을 확인하지 못했다. 표본 구간의 새 버퍼 생성 감소는 별도 성과이며, 더 큰 풀이나 비슷한 캐시를 다음 주력 과제로 선택할 근거는 아니다. Ultra 직접 비교에서는 해당 풀이 OFF였다. [S1], [S3]

현재 부족한 것은 다음이다. [S1]

- 이번 Ultra 교전의 연결된 CPU–GPU 시간축.
- 같은 Ultra 요청이 양쪽에서 만드는 실제 큰 pass·작업량의 동등성.
- 시험한 MVK3 보존 번들의 전체 소스·로컬 패치·컴파일 옵션 대응.
- 약 두 배의 처리율 차이 중 어느 구간이 실제 다음 제출을 늦추는지에 대한 설명.

**아직 CPU 병목, GPU 병목, drawable 병목, MRT 복사 병목 중 어느 하나를 확정하지 않는다.** 과거 잠금 화면의 drawable 대기나 다른 장면의 프로파일을 이번 교전 원인으로 가져오지 않는다.

## 3. 단계 0 — 기존 비교 기준 확인

### 지금 먼저 할 일

새 기준을 만들기 전에, 이미 직접 비교에 사용한 실행 파일·설정·콘텐츠·장면을 재사용할 수 있는지 확인한다. 확인만으로 충분하면 기존 FPS 시험 전체를 다시 돌리지 않는다.

- Native 시험 소스: `a3c7c6bfa93d09dac25755534195932d12fff41a`의 전체 엔진. [S4]
- Native 시험 binary SHA256: `b25a08287679847a420c37eaf3c201c9c95ad696e90d1b1eaa18e0cb08060942`.
- MVK3 시험 binary SHA256: `d715965659b977e05b8ccafe76fae0936cade1a7481871acff7eec876366f1aa`.
- 맵: Seths Ravine Remake 1.3.1. 콘텐츠·라이브러리·설정의 상세 identity는 기존 자료를 사용한다. [S5], [S6]
- Ultra, AA0, 관전자 전체 시야, 동일 카메라, 같은 초기 상태·seed·예열·측정 구간을 우선 기준으로 삼는다.
- Native는 PREPARE1/BEGIN0, worker1, FINAL_COLOR1, MODEL_TYPE_FACTS1, SCREEN_STATE_ELISION1을 유지한다. STORAGE_POOL0 및 D/Q/U0, Sepia OFF도 유지한다. 나머지는 실제 child environment 기록을 따른다.
- 화면은 전면·잠금 해제 상태를 확인한다. 전원 조건과 백그라운드 부하를 기록하고, clean 성능 측정과 프로파일/Validation 실행을 분리한다.

이 문서를 담은 브랜치는 문서 게시용이다. **그 브랜치의 main 기반 엔진을 위 시험 엔진 대신 빌드하면 안 된다.** 분석 대상 소스는 S4의 고정 커밋이다.

### 완료 조건

두 엔진에 대해 실제 실행할 binary·라이브러리·콘텐츠·child flags·장면의 대응표를 작성하고, 재사용 가능 또는 다른 점을 명시한다. MVK3 소스 대응이 불완전하다는 이유로 실행 비교를 무기한 막지는 않는다. 대신 해당 소스를 추정해 성능 원인으로 단정하지 않는다.

**이 단계에서는 새 캐시·풀·shader·queue-depth 변경을 하지 않는다.**

## 4. 단계 1 — 실행 지도와 시간축을 함께 비교

전체 저장소 재독해부터 시작하지 않는다. 같은 역할의 실제 작업을 대조하고, 시간이 갈라지는 위치를 찾는다. 실행 지도와 시간축은 하나의 관측 단계에서 서로를 설명하도록 구성한다. 모든 효과의 완벽한 동등성을 먼저 입증하느라 시간축 수집을 미루지 않는다.

### 4.1 함수 이름이 아니라 같은 역할을 비교

| 의미 단위 | 관측할 작업 | 주의점 |
|---|---|---|
| 시뮬레이션·Lua·capture | 갱신 횟수, snapshot·pose·packing, UI/체력바 생성 | 렌더 FPS 차이로 실행 빈도가 달라질 수 있음 |
| 유닛·그림자·반사·본화면 | 각 경로의 모델/instance·draw·준비 횟수 | GL 호출 수와 Metal 호출 수의 단순 일치가 목표가 아님 |
| 조명·후처리 | 활성 pass, 내부 크기·format·sample count | 옵션 이름만으로 실행을 확정하지 않음 |
| 중간 이미지 | copy·resolve·store/load·보존 범위 | 호출 수와 실제 byte/시간을 구분 |
| 제출·표시·회수 | 명령 준비, commit, GPU 실행, event/feedback, drawable, owner release | 같은 시간의 중복 합산 금지 |

상세 counter나 GPU capture를 사용할 수 있으면 큰 차이를 확인하는 데 활용한다. 도구가 제공하지 않는 항목은 미확인으로 남긴다. 한 대표 frame의 capture만으로 40초 전체 교전의 작업량을 확정하지 않는다.

### 4.2 필요한 시간 관계

기존 trace와 현 Mac에서 사용할 수 있는 Time Profiler / Instruments의 Metal·게임 성능 도구를 우선 사용한다. 먼저 실제 수집 가능한 항목을 확인한다. 새 대형 계측 프레임워크는 만들지 않는다.

각 엔진에서 다음 질문에 답한다.

1. Main이 진행을 멈춘 동안 렌더 worker 또는 드라이버 스레드는 CPU 작업을 하는가, 다른 완료를 기다리는가?
2. GPU는 그동안 이전 작업을 실행하는가, 다음 제출을 기다리는가?
3. GPU 완료 뒤에도 feedback·callback·residency·owner 해제 때문에 다음 진행이 늦어지는가?
4. drawable 확보·표시 또는 다른 제한 조건이 전체 진행을 지배하는가?
5. MVK3는 같은 역할의 작업을 언제 완료하며, 어떤 작업을 겹쳐서 수행하는가?

Native의 incoming capture / executing job / retired submission 식별자를 연결한다. 양쪽 엔진의 프레임 번호를 그대로 같은 사건으로 간주하지 않는다. 관측 가능한 simulation 구간·작업 의미로 대응시키며, 서로 다른 시계는 검증된 변환 없이 직접 빼지 않는다.

초당 호출 수만 비교하지 않는다. 더 빠른 쪽이 더 많은 프레임을 만들므로, **프레임당 작업·simulation 갱신당 작업·초당 작업을 구분**한다. inclusive profile 표본을 함수별 시간처럼 더하거나 main Join에 포함된 worker wait를 다시 합산하지 않는다.

계측 실행과 clean 성능 실행은 별도다. capture/serial 측정 등으로 실행 겹침이 달라졌다면 그 결과를 정상 runtime 처리율로 사용하지 않는다. GPU 사용률 평균 하나, 함수 경과 시간 하나 또는 `in-flight=1` 하나로 병목을 판정하지 않는다.

### 완료 조건

다음 세 분류 중 어느 설명이 큰 차이와 가장 잘 맞는지, 증거와 미확인 부분을 적는다.

- **더 많은 일을 한다:** Native에 중복 준비·추가 draw/pass/copy가 있음.
- **비슷한 일을 더 느리게 한다:** 작업량은 유사하나 CPU 준비 또는 GPU 작업 비용이 더 큼.
- **겹칠 수 있는 일을 직렬로 한다:** source·제출·완료·표시 경계에서 유효 작업 진행이 막힘.

혼합 원인도 허용하되 가장 큰 활성 구간 하나를 우선 후보로 정한다. 시간축이 부족하면 부족한 부분만 보완한다. 아직 구분되지 않았다면 성능 코드 PR을 시작하지 않는다.

## 5. 단계 2 — 가장 큰 차이 하나를 가르는 최소 실험

측정 결과가 요구하는 실험 하나만 고른다. 아래는 선택지이며, 전부 순서대로 실행하라는 목록이 아니다.

| 의심되는 원인 | 최소 진단 변경 | 해석의 한계 |
|---|---|---|
| 픽셀·화면 크기 관련 GPU 비용 | 같은 장면·카메라·종횡비에서 해상도만 축소 | 반응이 없다고 CPU 병목으로 확정할 수 없음 |
| 모델 수에 따른 반복 준비 | 같은 맵·설정에서 통제한 모델 규모 비교 | 실제 교전의 simulation·효과와 구분; 맵을 함께 바꾸지 않음 |
| 특정 그림자·반사·후처리 경로 | 양쪽에서 같은 기능 하나만 변경하고 실제 활성 경로 확인 | 기능을 꺼서 얻은 FPS는 최종 최적화가 아님 |
| 대기·제출 직렬화 | 연결된 job/submission의 선행 조건과 유휴 구간 추가 관측 | 위험한 Join 삭제나 GPU queue 확대를 진단 대용으로 쓰지 않음 |

비교할 값은 Native FPS 하나가 아니라 양쪽의 차이다.

```text
G = Native의 처리 주기 - MVK3의 처리 주기
```

둘 다 빨라졌다는 사실과 G가 줄었다는 사실을 구분한다. G의 변화 역시 상호작용을 포함할 수 있으므로 한 기능의 순수 독점 시간으로 간주하지 않는다.

### 완료 조건

하나의 원인 카드에 다음을 작성한다.

- 관측된 구간과 현재 활성 조건.
- Native/MVK3의 작업량·시간 차이와 원자료 위치.
- 관련 파일·함수·고정 커밋·행 범위.
- 가설, 반대 설명, 이를 가른 관측.
- 제안할 수정의 경계, 필요한 소유권·GPU 순서 증명과 위험.
- 기대하는 변화의 방향 및 검증 지표. 실측 근거 없는 FPS 숫자는 넣지 않음.

## 6. 단계 3 — 관련 코드만 깊게 비교하고 한 원인을 수정

실측에서 정한 의미 단위의 양쪽 호출 경로를 읽는다. 다음은 결과별 조사 방향이지 확정 결함 목록이 아니다.

| 확인된 차이 | 집중할 소스 |
|---|---|
| 같은 모델 상태를 shadow/reflection/main에서 필요 이상으로 반복 준비 | 원본 갱신·capture·snapshot 수명·패스 간 공유 |
| 비슷한 작업량인데 GPU 모델 패스가 비쌈 | 실제 shader/pipeline, specialization, 데이터 배치·stage 입력 |
| 추가 pass/copy/resolve가 큼 | 논리 이미지 버전, 이전 내용 보존, producer–consumer 순서 |
| CPU–GPU 사이의 노출 공백이 큼 | 제출 시점, Join·retirement·drawable 경계 |
| GPU 완료 이후 정리가 큼 | feedback·callback·residency·owner release |

MVK3의 최신 소스를 시험한 번들의 소스라고 가정하지 않는다. 필요한 부분부터 binary·library 버전과 대응시키고, 불명확한 compile flags·local patches는 미확정으로 표시한다. 원본 GLSL이 같다는 사실만으로 실제 GPU 코드와 specialization도 같다고 취급하지 않는다.

**수정 PR은 하나의 원인과 하나의 성공 기준을 가진다.** 그 수정이 상위 계약과 하위 사용처를 함께 바꿔야 안전하다면 함께 바꾼다. 독립적인 cache, skinning, shader, queue 변경을 같은 PR에 추가하지 않는다. 화면·효과·게임 의미와 GPU reader 수명을 보존하며 retain/pin/검증을 근거 없이 지우지 않는다.

### 완료 조건

관련 코드와 테스트가 준비되고, 어떤 경과 구간 또는 작업량이 왜 줄어야 하는지 설명된다. 호스트 테스트·syntax 검사·Mac 전체 빌드·실제 Metal 실행을 구분해 보고한다. 준비된 패치가 있다고 효과가 입증된 것으로 기록하지 않는다.

## 7. 단계 4 — 검증하고 결론을 낸 뒤 다음으로 넘어간다

같은 장면·동일 조건에서 변경 전후를 비교한다. 가능하면 같은 바이너리의 단일 선택지로 비교하고, 불가능하면 각 바이너리·소스·build flags를 별도로 고정한다. 프로파일/Validation과 clean 성능 시험은 분리한다.

평균 FPS만 보지 말고 관련 구간 시간, 작업량, 느린 프레임, 화면·효과, 필요한 수명 경로, 메모리 비용을 함께 기록한다. 실제 present/GPU 완료율을 측정하지 않았다면 DrawScreen 처리율과 혼동하지 않는다. 나쁜 회차와 실패 기록을 보존하고, 반복 수와 변동성을 명시한다.

| 판정 | 처리 |
|---|---|
| 목표 구간과 전체 성능의 개선이 충분히 뒷받침됨 | 검증 범위와 잔여 위험을 밝히고 채택 후보로 제안 |
| 작업량은 줄었지만 FPS 이득 미확인 | 별도 보류; 다음 성능 후보의 필수 기반으로 자동 편입하지 않음 |
| 안전성 실패 또는 반복되는 회귀 | 기각/수정하고 기존 기준 유지 |
| 조건 불일치·측정 불충분 | 결론 유보; 해당 결함만 보완하고 다른 최적화를 추가하지 않음 |

두 회차씩의 작은 차이를 통계적 동등성·무회귀로 선언하지 않는다. 일부 counter 감소를 순수 CPU·GPU 시간 감소로 대신하지 않는다. 작은 변경을 여러 개 합치면 큰 이득이 날 것이라는 상호작용도 별도 가설이며, 개별 결과 없이 자동 합산하지 않는다.

**채택·보류·기각을 기록한 다음에만 다음 성능 가설을 시작한다.** 채택 후보의 main 병합·릴리스·Homebrew 갱신은 별도 승인·배포 작업이다.

## 8. PR와 브랜치 운영

이 계획 문서는 기존 실험 PR #7 뒤에 쌓지 않는 독립적인 docs-only 변경이다. 이후 작업도 다음처럼 구분한다.

| 단위 | 담을 내용 | 담지 않을 내용 |
|---|---|---|
| 계획 문서 | 단계·판정 기준·고정 자료 링크 | 성능 코드, 새 실험 결과인 척하는 수치 |
| 비교 감사 기록 | 단계 0–2의 실행 조건·원자료·분류·원인 카드 | 여러 미검증 성능 패치 |
| 원인 하나의 수정 PR | 단계 3의 관련 코드·테스트, 단계 4의 결과와 처분 | 다른 병목의 후보, 배포 변경 |
| 다음 수정 PR | 앞선 결과를 바탕으로 새로 선택한 원인 | 앞선 보류 후보를 설명 없이 상속한 변경 |

증거 파일은 새 디렉터리/고정 커밋으로 보존하고 이전 실패·결과를 덮어쓰지 않는다. 문서만 여러 PR로 쪼개는 것이 목적은 아니다. **새 성능 가설을 검증 중인 PR에 계속 얹지 않는 것이 목적이다.**

실험 코드 기반은 자동으로 최신 PR head나 main을 고르지 않는다. 현재 비교에 사용한 기준 또는 명시적으로 채택한 후속 기준을 사용한다. 반드시 필요한 미병합 의존성이 있으면 그 커밋·이유·비교 조건을 적고, 무관한 후보는 포함하지 않는다.

## 9. 담당자에게 전달할 첫 작업 지시

> 지금은 단계 0–1을 수행한다. 기존 Ultra·AA0 교전의 두 바이너리와 실제 child 설정을 확인하고, 같은 역할의 실행 지도 및 CPU–GPU 시간 관계를 비교한다. 기존 계측을 우선 쓰고 필요한 누락만 보완한다. 결과를 제시하기 전에 새 cache·pool·queue-depth·shader 최적화를 추가하지 않는다.
>
> 결과는 ‘추가 작업 / 동일 작업의 높은 비용 / 불필요한 직렬화’로 구분하고, 가장 큰 차이 하나와 남은 반대 가설을 적는다. 그다음 필요한 최소 원인 분리 실험을 선택한다. 단계 2의 원인 카드가 성립한 뒤에만 관련 코드 수정 PR을 만든다.
>
> 기존 작은 후보는 보존하되 주력 작업에서 보류한다. 다음 후보의 성공 기준은 생략한 호출 수가 아니라, 실제 프레임 진행을 막던 구간이 어떻게 바뀌었는가다.
