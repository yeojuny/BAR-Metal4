# BAR Native Metal 4 성능 감사 인계 · 2026-11-23

## 어디까지 왔나

Seths Ravine 전투의 작업 기준은 Native R03, cap2, AC 자동, Ultra AA0, 1512×950, 540~1740틱이다. 아래 평균 FPS와 1% low는 일시정지·GPU 캡처를 뺀 일반 실행에서 얻었고, 긴 프레임도 모두 포함했다. Grass를 조밀하게 재배열한 판과 픽셀을 보존하려고 드로우 끝만 자른 판은 같은 바이너리로 비교했다. MVK3 두 값은 이전 날짜의 별도 실행이다. 현재 Grass 후보를 MVK3와 직접 짝지어 돌린 기록은 없다.

## Grass에서 이번에 확인한 것

- 1665틱에 원본 21,504개 중 실제 풀은 304개였다. 끝만 잘랐을 때 남은 14,054개 안에 맨 앞의 빈 슬롯 5,321개와 중간 빈 슬롯 8,429개가 있었다. 새 후보는 원래 인스턴스 버퍼와 살아 있는 슬롯 번호·순서를 유지한다. 드로우 시작을 기준으로 정렬된 256슬롯 블록에서만 오랫동안 비어 있는 구간의 안쪽을 건너뛴다. 생존 슬롯 주변에는 빈 블록을 남긴다. 안전 조건이 충족되지 않으면 기존 끝 자르기를 쓴다.
- 첫 1665틱 화면 검사는 15개 모드를 무작위로 섞어 각 4회씩 같은 입력에서 재생했다. 256 기준으로 중간만 건너뛰면 12,006개, 앞과 중간을 함께 건너뛰면 8,422개였다. 후자는 기존 7드로우에서 10드로우가 되었고, 제출 슬롯은 40.1% 줄었다. 두 후보 모두 원본 및 끝 자르기와 비교해 모드별 관측값이 분리되는 색상·깊이·스텐실 픽셀이 0개였다. 더 작은 8~128 경계의 중간 분할에서는 반복되는 색상 차이가 있었다. 동일 모드 안에서도 픽셀이 변동했다. 이는 여러 차례의 재생 결과이며 단일 화면 전체의 비트 일치 보장은 아니다.
- 별도 셰이더는 크기가 0 이하인 풀의 정점을 행렬 계산 전에 종료한다. 1665틱 기존 끝 자르기 위에서 두 모드가 같은 14,054슬롯·7드로우를 처리했다. 각 8회 재생, 모드별 관측값이 분리되는 픽셀 0개. 최종 결합판과 이 독립 실험은 서로 다른 실행이다.
- 최종 소스의 CPU 대조 634,801건 중 59,343건에서 앞이나 중간의 슬롯이 실제로 생략됐다. 이 검사는 주소·순서·예외 비트 처리에 대한 근거다. Shallow Straits 지형 원본에는 풀 밀도가 0보다 큰 셀이 4,824/36,864개였고 검증용 카메라와 설정을 준비했다. 두 번째 맵의 실제 렌더링, 최종 결합판의 600·1665틱 픽셀, 실제 전투 FPS는 후속 검증 대상이다.
- 마지막으로 열린 창은 Seths 1665틱 진단용이었다. 게임이 LuaRules의 `api_pbr_enabler.lua`와 LuaUI의 `api_blueprint.lua`를 가상 파일시스템에서 찾지 못해 전투 제어기가 로딩되지 않았다. 이 실행은 실패로 기록했다. 파일 탐색이 실패한 근본 원인은 미확정이다. 사용자가 실행 중단을 요청한 뒤 추가 벤치와 GPU 진단은 진행하지 않았다.
- GroundDecal 트랙 조기 제외는 OFF를 기준으로 한다. 끝 자르기 기준에서 기존 OFF는 87.78/61.33, ON은 85.93/60.24였다. 지형 상세 재질 읽기 생략도 OFF다. 픽셀 검증과 동작량 감소만으로 패치를 채택하지 않는 근거 사례다. [트랙 OFF/ON](audit-inputs/early-track-fps.json) · [지형 결과](audit-inputs/prior-terrain-results.md)

## Native가 엔진 내부 사정을 알아서 생략할 수 있는 작업은 무엇인가

MVK3는 이 프로젝트가 이미 튜닝한 실전 기준이다. Native와 MVK3가 공유하는 개선, MVK3 비교판에만 있는 개선, Native 경로에서 추가된 의무를 빌드·스위치별로 기록한다. KosmicKrisp(KK)의 BAR 동일 조건 실측은 이 자료에 없다. 외부 규모감으로 LunarG의 M3 Pro GFXBench Aztec High에서는 Metal 14,416, MoltenVK 10,864, KK 11,672로, Metal이 각각 32.7%, 23.5% 높다. 동기화 재설계만으로 KK 점수도 한 단계에서 9.1% 올랐다. 비교 API·기기·워크로드가 정해진 사례다. 별도의 2021년 Khronos Q&A에서 언급된 25~30%는 Dota 2 사례에서 추정한 구현 내부 CPU 오버헤드였다. [LunarG XDC 자료, 14~15쪽](https://www.lunarg.com/wp-content/uploads/2026/09/XDC-2026-KosmicKrisp-LunarG.pdf) · [Khronos Q&A, 문항 22](https://www.khronos.org/assets/uploads/developers/presentations/Vulkansed_Fall_2021_-_QA_Summary.pdf)

Native 87.41 FPS는 11.44ms/프레임, MVK3 94.46은 10.59ms다. 동률까지 약 0.85ms가 필요하다. 이 MVK3보다 20~30% 높은 113.35~122.80 FPS를 탐색 목표로 설정하면 Native 현재치에서 약 2.62~3.30ms를 줄여야 한다. 아래는 후보이며 이 시간을 회수할 수 있다고 예측한 것이 아니다.

1. **같은 픽셀을 여러 번 메모리로 왕복시키는 경계.** 가장 먼저 지형·G-buffer가 깊이·법선·색을 쓴 뒤 데칼·조명이 읽는 경계 한 곳을 추적한다. 생성·마지막 소비 드로우, 텍스처 뷰·밉·샘플, 좌표·필터, 블렌딩·깊이·스텐실 순서, 이후 소비자를 확인한다. 같은 샘플의 현 픽셀만 읽는 호환 작업이면 같은 렌더 패스에서 attachment 읽기/타일 내 접근을 검토한다. 옆 픽셀이나 변환된 UV를 읽는 distortion, 화면 밖 소비자, 화면 깊이 스냅샷이 필요한 경로는 원래 저장 의미를 보존한다. 마지막 소비 뒤에는 store 생략, 일시 attachment라면 memoryless 사용 가능성을 따로 본다. 패스 이름이나 encoder 개수만으로 실제 메모리 왕복을 추정하지 않는다. 캡처의 load/store와 GPU 읽기·쓰기 대역폭, 같은 장면의 전체 GPU 완료 시각으로 확인한다. [Apple GPU 타임라인](https://developer.apple.com/documentation/xcode/analyzing-apple-gpu-performance-using-a-visual-timeline) · [Metal 4의 attachment 활용](https://developer.apple.com/videos/play/wwdc2025/254/)
2. **결과에 영향을 줄 수 없는 데칼 작업을 생성 단계에서 없앨 기회.** 과거 1275틱 GroundDecal은 양쪽 모두 인스턴스 24,335개, 프래그먼트 단계는 Native 5.23ms·MVK3 2.46ms였다. 이후 수정 전 캡처이고 덮인 샘플 및 모든 입력 바이트의 동등성은 미확인이다. 먼저 두 경로의 인스턴스 바이트, 화면 덮임, 실제 프래그먼트 수, 연산·텍스처 사용량을 대조한다. 겹침이 지배하면 엔진이 아는 트랙 범위에서 보수적인 화면/타일 후보 목록을 만들어 원래 ID·블렌드 순서를 유지하는 경우를 검토한다. 일부 트랙만 바뀐 프레임에 모든 인스턴스 목록을 다시 만드는 비용과 후보 생성용 compute→render 동기화도 함께 비용에 넣는다. [이전 대응 패스](audit-inputs/capture-pass-costs.json) · [같은 틱에도 GameDecal 입력이 달랐던 사례](audit-inputs/matched-workload-limits.md)
3. **엔진이 아는 변경 시점과 자원 수명을 Metal에 직접 표현할 기회.** 지형/아틀라스처럼 오래 가는 자원, 매 프레임 바뀌는 자원, cap2에서 앞 프레임도 읽고 있는 버전을 나눈다. 이미 캐시를 적용한 큐브맵이나 argument table은 실제 누락이 반복되는 경우에만 다시 조사한다. 아직 반복되는 등록·바인딩은 변경된 부분만 갱신하고, 마지막 소비가 끝난 버전부터 재사용할 수 있는지 확인한다. 배리어 범위 축소는 실제 생산자·소비자 및 alias 관계를 근거로 한다. AC 자동 과거 전투에서는 제출 사이 GPU 공백 3,317개가 평균 0.091ms, 중앙값 0.082ms였고, 1ms 초과는 2개였다. 이 공백을 전부 없앤다는 가정조차 당시 평균 약 0.09ms이므로 평균 격차에 대한 우선순위는 낮다. 드문 등록 지연은 1% low와 표시 간격을 기준으로 별도 검토한다. [원시 공백](audit-inputs/commit-gaps.csv) · [통계](audit-inputs/cap2-gaps-ac-auto.json) · [Metal 4의 큐·바인딩](https://developer.apple.com/documentation/metal/understanding-the-metal-4-core-api) · [Apple 자원 동기화](https://developer.apple.com/documentation/metal/resource-synchronization)

감사 결과에는 각 경계의 마지막 생산자·첫 소비자, 현재 소스에서 도달하는 조건, 기존 채택 패치와의 중복, 영향을 받은 프레임 비율, 관측 비용, 회수 가능한 상한, 정확성을 깨는 반례를 남긴다. 이미 합친 Distortion은 과거 일반 벤치에서 전체 프레임당 0.030ms를 줄였고 1% low는 2.80% 낮아졌다. 새 경계도 패스 시간을 더해서 이득으로 계산하지 않고, 겹친 GPU 작업을 한 번만 세며 화면에 도달한 임계 경로를 기준으로 판단한다. 이 문서는 기존 캡처와 결과에 기반한다.
